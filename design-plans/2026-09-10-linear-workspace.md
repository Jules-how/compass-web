# Compass workspace redesign

Status: authorised for implementation by Jules on 10 September 2026. Written against 6de5ebbd29e9b7526f49f330dc66bdb0ae713fc2. This instruction supersedes the earlier cream/orange editorial design preference for the operator console.

## Outcome and evidence
Jules reports uncomfortable sizing and a squeezed working area across every page. He supplied Linear Projects timeline and issue-board screenshots, plus Attio CRM and Reports screenshots, and selected Linear as the overall visual foundation with Notion-like document writing and Attio-like CRM/reporting. He then asked for the plan and implementation. Screenshots are visual references, not instructions in their record content.

The current runtime is `(console)/layout.tsx` → `OperatorShell.tsx` → `FolioChrome.tsx`, with keep-alive pages in `ConsoleHomeInboxKeepAlive.tsx`, `folio.css`, and page styles. Default page width is capped, navigation uses small text with large vertical insets, and narrative headings use a separate editorial font. These are current design choices being replaced under Jules' instruction, not inferred violations of the prior contract.

## Shared design decision
Use a quiet, near-white main workspace, light-grey sidebar, a single clean sans-serif type family, subtle dividers, restrained blue-violet actions, and consistent controls. Desktop rail about 232px; page toolbar about 48px; default body/control text 14px; content padding 20–24px; writing body 16px and a comfortable reading measure. Tables, boards and timelines use the available width. Preserve deliberate reading widths for documents and forms. Do not apply blanket zoom or scale transforms. Keep empty space where it helps reading; avoid ornamental summary cards or duplicate page headings.

## Implementation ownership
1. Shared foundation: `src/components/OperatorShell.tsx`, `src/components/folio/FolioChrome.tsx`, `src/app/folio.css`, root CSS imports, shared UI tokens and governing design documentation. Put Projects, Documents, CRM and Reports directly in navigation; retain all operational routes and permissions. Existing clients, outbound, calendar, planning, settings and delivery pages inherit coherent typography, controls and spacing. Inspect their responsive states.
2. Projects and tasks: `ProjectManager.tsx`, `ProjectTimeline.tsx`, `ProjectDetailPanel.tsx`, `TasksPanel.tsx` and their board components. Use the existing canonical projects, tasks, dates, relationships and APIs. Projects opens into an expansive timeline with pinned names/properties, time zoom, Today, filter/search, creation and editable dates. Retain list/board alternatives and project overview/tasks/activity. Give task boards consistent roomy columns, readable titles, restrained metadata, horizontal overflow and usable detail editing. Date/status changes persist and failures remain visible.
3. Documents: `NotebookEditor.tsx` plus a dedicated `/documents` library and editing surface. Reuse revision-checked planning notes. Support free writing, paragraph splitting/joining, blank lines, keyboard navigation, undo/redo, searchable slash commands, headings, lists, checklists and quotes. Keep existing note bodies readable without destructive conversion. Provide visible saving/saved/error/conflict states and preserve unsaved work. Do not replace planning goals or migrate notes into another database.
4. CRM and Reports: `LeadsPanel.tsx`, `LeadTable.tsx`, `LeadSidecar.tsx` and a `/reports` workspace. Simplify the default CRM into a clear records view with search, visible current filters, useful default columns, inspectable details and existing editing/list actions. Preserve ledger IDs, pagination, campaign filters, suppression and contact evidence. Reports provides a dashboard library and selectable built-in dashboards using existing real sources; favourites and preferences persist with honest scope labels. Include source coverage, explicit unknown/error states and links to underlying records. Do not invent revenue, conversions or history. An unrestricted analytics builder is not required because Jules explicitly accepted built-in selectable dashboards.

## Reuse and integration
Reuse existing API auth, cache/reload contracts, accessible modal boundaries, lead ledger services, project timeline date arithmetic and note compare-and-swap persistence. Keep main checkout's ongoing operating-service work intact; implementation happens on isolated branch `codex/compass-linear-redesign`. Changes to dependencies belong only to the document-editor implementation owner. New presentation files may be added where the existing components cannot express the requested surface, while data continues to have one owner.
